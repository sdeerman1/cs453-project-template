# Graduate Extension Lessons Learned

The most important technical concept I learned in this project was how to implement authentication. I have never had to implement such robust authentication in a project before, so this was a crucial lesson for me to learn and will be very useful as I can apply it to my projects going forward. In this project, I used the library bcryptjs to hash passwords before storing them in the database, which allows for user authentication without storing plaintext passwords. Storing plaintext passwords in a database is a huge security vulnerability, as this is sensitive data that attackers will try to steal. After hashing the passwords, the user data is safe even if the database is compromised. I also used JSON Web Tokens to ensure that each user has been authenticated before allowing them to access or modify the projects and tasks in the database. This is another layer of security that keeps the data safe, and does not allow attackers full reign over modifying the database.  
  
Database design, authentication, and authorization are three extremely important components of system architecture, and are crucial to the security of the system. A strong defense system will protect our data and our users from malicious actors. Authentication refers to the process in which the system establishes the identity of the user, and authorization uses that identity to grant the user certain permissions. Authorization cannot happen without first authenticating the user, and the process in which the user is authenticated dictates how the authorization can take place. In this project, I used JSON Web Tokens for authentication, which returned a bearer token after the user logs in. The system only authorized the user to send certain requests if the user supplied this bearer token with the request, which certifies that the user is authorized to receive the information. These are simply concepts without implementing them in the database design. In my database, I have a “users” table that holds an id, name, email, password hash, role, and the time the user was created. The password hash is what allows the user to first be authenticated when logging in, as I compare the user’s entered password with the password hash. The user’s role is what allows for authorization, as I check the user’s role before allowing or preventing the user from completing certain tasks.  
  
One design decision I made was to extend the separation of concerns by including an “error.ts” file that handles mapping HTTP status codes to the different error types. This allows my routes and services to focus on business logic without having to map the error codes. It also allows for standard formatting of JSON error messages and allows the code to stay clean and organized. The downside would come if this application were to be expanded, where the “error.ts” file becomes cluttered with dozens of small, very specific error types. This also may become a problem with debugging if the stack trace points to the “error.ts” file instead of the actual code that is causing the error.  
  
The biggest difficulty I encountered was authorizing the user to modify or delete a task that belonged to them. This was slightly difficult as I had to fetch the task by its ID, check the task’s project ID, fetch the project by its ID, and then check the project’s owner ID. I then had to compare this owner ID to the user’s ID from the JSON Web Token (JWT), and also include the stipulation that the user can modify or delete tasks they don’t own if they are an admin. This took some trial and error and I ended up modifying the JWT slightly from the example code in class to ensure I could access the user ID and role from anywhere in the application.  
  
If beginning again, I would have looked up how to implement separation of concerns earlier. It was not too difficult to figure out using resources from the internet, but I had already completed Checkpoint 1 with all the logic contained in the “server.ts” file. When I finally separated the logic into separate route and service files, with separate middleware and error files as well, it felt like I had to re-do all the work I had already done for Checkpoint 1. I could have saved a lot of time if I had started out separating the logic.  
  
The biggest advice I have is to start early. Coding in general is a lot of trial and error, and this project felt like I was learning how to do everything as I was implementing it into the project. Utilize the internet, and always check for error messages in the console. Debugging unknown errors was slightly difficult after implementing error handling when the error just returns “500 Internal Service Error” and sends nothing else to the console, but I was usually able to fix the error as most errors returned robust messages where I was able to research how to fix them.   
  
The biggest security risk would be to store plaintext passwords in the database. Attackers may try to steal the password database, and having plaintext passwords stored means the attackers can access each user's password. Hashing the passwords before storing them means that even if the database becomes compromised, the information stays safe. Storing the password as a hash turns it into a long, random string that cannot be reverse-engineered to access the original password string. This also provides protection from insider threats. Even database engineers or software engineers working on the system cannot view users' passwords. This is the standard in industry and is a non-negotiable that developer absolutely cannot overlook.
